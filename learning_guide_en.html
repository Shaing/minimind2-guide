Question 1

What is Prefill?

🧭 First Principles

An autoregressive language model is a function: given t1, t2, ..., tk, predict t_{k+1}. Before generating the first new token, the model must "read" the user's entire prompt — embed each token, run them through all 16 Transformer layers, and compute every token's K and V. This one-shot batch processing is called prefill.

  • It runs exactly once per generate() call
  • It determines TTFT (Time To First Token) — the "thinking pause" the user feels
  • Attention cost is O(L²·D) — this phase is compute-bound

Question 2

What is Decode?

🧭 First Principles

After prefill, the model enters a token-by-token generation loop:

  1. Feed in only the token that was just generated (one token!)
  2. Embed it, compute Q/K/V — but K/V cover just this one new token
  3. Concatenate the new K, V onto the end of the cache. The cache now holds all history + this new token
  4. Compute attention: Q has 1 row (the new token), K/V have L+t rows (the full history)
  5. Emit logits → sample → return to step 1
  • Per-step cost is O((N+t)·D) — grows linearly with conversation length
  • The bottleneck is memory bandwidth (reading an ever-growing cache) — this phase is memory-bound
  • It determines TPOT (Time Per Output Token) — the "typing speed" the user feels

Question 3

What is the KV Cache?

🧭 First Principles: why can we cache K and V, but not Q?

The math makes it obvious. For token i at position p:

  • K_i = W_k · embed(token_i) — depends only on token_i and position p
  • V_i = W_v · embed(token_i) — depends only on token_i and position p
  • Q_i = W_q · embed(token_i) — also depends only on token_i and position p

The key difference: in a causal model, computing the attention output for token t requires

  • Only Q_t (the current token's Q) — so Q only ever needs the current row
  • The full K_0..K_t and V_0..V_t (every past + current token's K, V)

And critically, K_i and V_i never change once computed — appending future tokens doesn't affect past K/V. So: compute K, V once and store them; recompute Q every step (it's only one row anyway).

Per-layer caches are collected into a list — model_minimind.py:417-426:

model_minimind.py:417 — 16 layers, one cache eachpresents = []
for layer_idx, (layer, past_key_value) in enumerate(zip(self.layers, past_key_values)):
    hidden_states, present = layer(hidden_states, position_embeddings,
                                   past_key_value=past_key_value, ...)

So the cache is a list of length 16 layers, where each element is a (K, V) tuple of shape [B, L_so_far, Hkv, d]. The whole cache flows through the past_key_values object and is updated iteratively inside generate()'s loop.

model_minimind.py:140-147 is all there is to GQA:

model_minimind.py:140 — repeat_kv (zero-copy view expansion)def repeat_kv(x: torch.Tensor, n_rep: int) -> torch.Tensor:
    bs, slen, num_key_value_heads, head_dim = x.shape
    if n_rep == 1:
        return x
    return (
        x[:, :, :, None, :].expand(bs, slen, num_key_value_heads, n_rep, head_dim)
            .reshape(bs, slen, num_key_value_heads * n_rep, head_dim)
    )

The trick: expand() is a view, not a memory copy. The actual cache still holds only 2 KV heads. The broadcast to 8 exists only as a logical view at compute time and gets fused away inside the attention kernel.

🆚 GQA vs MQA — Why GQA Strictly Dominates MQA

VariantQ headsKV heads (G)KV cache sizeQuality
MHAHH (one-to-one)H × seq_len × dHighest
MQAH1 (all shared)1 × seq_len × dNoticeably degraded
GQA ✅HG (1 < G < H)G × seq_len × dNear MHA

MQA (Multi-Query Attention) is the extreme edge of the GQA design space: G = 1, meaning all Q heads share the exact same KV pair. The problem: 8 Q heads each bring a different "question," yet only one K/V "memory" answers all of them. The expressiveness bottleneck is on the KV side, and experiments show measurable quality loss on long-context and complex reasoning tasks.

With GQA at G=2, each KV head covers a narrower semantic subspace, which is enough to recover most of that quality — while the cache is still only 1/4 of MHA. That's the sweet spot.

📜 Historical context
MQA was proposed by Shazeer in 2019; GQA followed from Ainslie et al. in 2023 — four years later. Today, LLaMA-2/3, Mistral, and Gemma all use GQA; MQA survives only in extreme memory-constrained edge deployments. The practical consensus is H/G = 4–8 as the sweet spot: larger G approaches MHA quality, smaller G saves more memory.
Question 5

The Nature of Multi-turn Chat

🧭 First Principles: the LLM is stateless

An LLM forward pass remembers absolutely nothing between generate() calls. The only way to make a chatbot "remember" the conversation is to splice all past turns into one long string and re-stuff it into the prompt.

📐 Two strategies

StrategyProsConsThis project
A · Re-prefill every turn (naive) Stateless server, simple Slows down as history grows; redundant compute ✅ Used
B · Session-level KV cache Reuses past turns' K/V Complex memory management (vLLM / SGLang territory) ❌ Not implemented

Question 6

Why is the Context Window 4096?

🧭 First Principles: three independent gates

The context window is a hard ceiling on prompt + generated. It's determined by three independent factors — break any one and everything falls apart:

  1. Positional-encoding limit (structural hard cap) — RoPE pre-computes the freqs_cos/sin buffers at shape [max_position_embeddings, head_dim]. Index past it and you get IndexError.
  2. Training data distribution — the model only saw sequences up to length N during training. Go beyond and it has never "seen" that regime — semantic quality collapses.
  3. Compute and memory cost — attention is O(L²), the KV cache grows linearly. From 4K → 32K: attention cost balloons 64×.

📍 Source Pointer — where the context cap is enforced

model_minimind.py:393-397 — RoPE buffer precomputefreqs_cos, freqs_sin = precompute_freqs_cis(
    dim=config.hidden_size // config.num_attention_heads,
    end=config.max_position_embeddings,    ★ 32768 — this is the hard wall
    rope_base=config.rope_theta,
    rope_scaling=config.rope_scaling
)
self.register_buffer("freqs_cos", freqs_cos, persistent=False)
self.register_buffer("freqs_sin", freqs_sin, persistent=False)

🤔 Why specifically 4096?

Three reasons converged:

  • Power of two — GPU memory tiling, kernel block sizes, and CUDA warps (32) all prefer powers of two. 4096 = 2^12 lines up cleanly.
  • 2023's economic sweet spot — LLaMA-1 used 2048; LLaMA-2 doubled it to 4096. Doubling context = 4× attention cost. 4K was the maximum Meta could afford at the time, and the industry copied them.
  • Document length distribution — most web pages, code files, and book chapters fit within 4K. Beyond that, you need explicit data engineering.

🚀 How MiniMind2 pushes further: YaRN

MiniMind2's default context is 32K; with --inference_rope_scaling enabled, it stretches to 128K — without retraining!

model_minimind.py:108-128 — YaRN: Yet another RoPE extensioNdef precompute_freqs_cis(dim, end=int(32 * 1024), rope_base=1e6, rope_scaling=None):
    freqs = 1.0 / (rope_base ** (torch.arange(0, dim, 2)[: (dim // 2)].float() / dim))
    if rope_scaling is not None:
        orig_max, factor, beta_fast, beta_slow = ...
        if end / orig_max > 1.0:
            # ★ YaRN only "squeezes" the low-freq dims that would alias; high-freq dims stay intact
            corr_dim = next((i for i in range(dim // 2)
                            if 2 * math.pi / freqs[i] > orig_max), dim // 2)
            power = torch.arange(0, dim // 2, ...).float() / max(dim // 2 - 1, 1)
            beta = beta_slow + (beta_fast - beta_slow) * power
            # λ = (β·α - β + 1)/(β·α) — the standard YaRN formula
            scale = torch.where(torch.arange(dim // 2, ...) < corr_dim,
                                (beta * factor - beta + 1) / (beta * factor),
                                1.0 / factor)
            freqs = freqs * scale
💡 What makes YaRN elegant
Traditional Position Interpolation compresses every frequency uniformly, which destroys high-frequency representations. YaRN uses corr_dim to separate "low frequencies that should be squeezed" from "high frequencies that should be preserved" — a piecewise treatment that retains the most learned structure.

model_minimind.py:204-218 — manual path (decode + edge cases)else:

    scores = scores + torch.triu(
        torch.full((seq_len, seq_len), float("-inf"), ...),
        diagonal=1
    ).unsqueeze(0).unsqueeze(0)   # ★ causal mask (upper-triangular -inf)

    if attention_mask is not None:

        scores = scores + extended_attention_mask   # ★ padding mask
🔬 Why -inf instead of 0?
Because the next step is softmax. softmax(-inf) ≈ 0, so multiplying by V contributes nothing. Using 0 would still leave a non-zero weight after softmax normalization. Both masks compose by addition in log space — mathematically clean.
Question 8

Streaming Output — TextStreamer, TTFT vs TPOT

🧭 First Principles

Without streaming: the user waits TTFT + (output_len × TPOT) and sees the full answer at once.
With streaming: the user sees the first token immediately after TTFT, then a new token every TPOT interval.

📍 Source Pointer

eval_llm.py:63 — local CLI streamingstreamer = TextStreamer(tokenizer, skip_prompt=True, skip_special_tokens=True)
# skip_prompt=True means don't echo the prompt, only print generated tokens
scripts/serve_openai_api.py:59-68 — Server-Sent Events streamingclass CustomStreamer(TextStreamer):
    def __init__(self, tokenizer, queue):
        super().__init__(tokenizer, skip_prompt=True, skip_special_tokens=True)
        self.queue = queue

    def on_finalized_text(self, text: str, stream_end: bool = False):
        self.queue.put(text)        # push every generated token onto the queue
        if stream_end:
            self.queue.put(None)    # end marker
🎯 Operational takeaways
  • Prefill cost = TTFT: drives the "thinking pause" the user feels
  • Decode cost × output length = total streaming time: each token is fast but they add up
  • KV cache helps TPOT, not TTFT — to improve TTFT on repeated prompts you need cross-request prefix caching
