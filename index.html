Question 1

什麼是 Prefill？預填充階段

🧭 第一性原理 First Principles

一個 autoregressive LM 自回歸語言模型 是函數：給定 t1, t2, ..., tk，預測 t_{k+1}。要產生第一個新字之前，模型必須先「讀完」使用者整段提示 — 將每個 token 嵌入、跑過全部 16 層 Transformer、把每個 token 的 K/V 算出來。這個一次性的批次處理就叫 prefill。

  • 它每次 generate() 呼叫只發生一次
  • 它決定 TTFT（Time To First Token 首 token 延遲）— 使用者感受到的「思考停頓」
  • 注意力計算成本 O(L²·D) — 是 compute-bound運算瓶頸

Question 2

什麼是 Decode？解碼階段

🧭 第一性原理

Prefill 結束後進入逐字生成迴圈：

  1. 只把上一次剛生成的那個 token（1 個！）餵進去
  2. 嵌入、計算 Q/K/V — 但 K/V 只是「這 1 個新 token」的
  3. 新的 K, V 拼接到 cache 末端。現在 cache 包含所有過去 + 這個新 token
  4. 計算注意力：Q 只有 1 列（新 token），K/V 有 L+t 列（全部歷史）
  5. 輸出 logit → 採樣 → 回到步驟 1
  • 每步成本 O((N+t)·D) — 隨對話線性增長
  • 瓶頸是記憶體頻寬memory bandwidth（讀取愈來愈大的 cache）— 是 memory-bound
  • 決定 TPOT（Time Per Output Token 每 token 間延遲）— 使用者感受到的「打字速度」

Question 3

什麼是 KV Cache？KV 快取的本質

🧭 第一性原理：為什麼能快取 K 和 V，但不能快取 Q？

看數學就一目了然。對位置 p 的 token i：

  • K_i = W_k · embed(token_i) — 只依賴 token_i 和位置 p
  • V_i = W_v · embed(token_i) — 只依賴 token_i 和位置 p
  • Q_i = W_q · embed(token_i) — 也只依賴 token_i 和位置 p

關鍵差別：對因果模型而言，計算 token t 的注意力輸出時，

  • 只需要 Q_t（當前 token 的 Q）— 所以 Q 只算當前的就好
  • 需要 K_0..K_t 和 V_0..V_t（所有過去 + 當前 token 的 K, V）

而且 K_i, V_i 只要算過一次就不會變 — 之後再加新 token 也不影響舊 token 的 K/V。所以：K, V 算一次存起來；Q 每步重算（反正只有 1 列）。

model_minimind.py:140-147 就是 GQA 的全部魔法：

model_minimind.py:140 — repeat_kv (零拷貝 view 擴展)def repeat_kv(x: torch.Tensor, n_rep: int) -> torch.Tensor:
    bs, slen, num_key_value_heads, head_dim = x.shape
    if n_rep == 1:
        return x
    return (
        x[:, :, :, None, :].expand(bs, slen, num_key_value_heads, n_rep, head_dim)
            .reshape(bs, slen, num_key_value_heads * n_rep, head_dim)
    )

關鍵：expand() 是 view 操作，不複製記憶體。實際 cache 仍只有 2 個 KV 頭。擴展到 8 頭只在計算時作為「邏輯視圖」存在，並被 attention kernel 融合掉。

🆚 GQA vs MQA — 為什麼 GQA 嚴格優於 MQA？

方案Q 頭KV 頭 (G)KV cache 大小品質
MHAHH（一對一）H × seq_len × d最高
MQAH1（全共用）1 × seq_len × d明顯下降
GQA ✅HG（1 < G < H）G × seq_len × d接近 MHA

MQA（Multi-Query Attention）是 GQA 的極端特例：G = 1，所有 Q 頭共用同一組 KV。問題在於——8 個 Q 頭各自帶著不同的「問法」，卻只有一份 K/V「記憶」回應，表達能力的瓶頸卡在 KV 端，實驗上在長上下文與複雜推理任務上品質下降明顯。

GQA 的 G=2 已足夠讓每組 KV 頭承擔更窄的語意子空間，同時 cache 仍是 MHA 的 1/4。這是記憶體效率與模型品質之間的甜蜜點。

📜 歷史脈絡
MQA 由 Shazeer 於 2019 年提出，GQA 由 Ainslie et al. 於 2023 年才跟進。業界用了 4 年才找到更好的折中方案。現在 LLaMA-2/3、Mistral、Gemma 全部採用 GQA；MQA 僅在極端記憶體受限的邊緣設備場景仍有使用。實務上 H/G = 4–8 是公認的甜蜜點——G 越大越接近 MHA 品質，G 越小越省記憶體。

多輪對話的本質 Multi-turn Chat

🧭 第一性原理：LLM 是無狀態的

LLM forward pass 在每次 generate() 呼叫之間完全不記得任何事。讓 chatbot「記得」對話的唯一辦法：把所有過去輪次串成一個長字串重新塞進提示。

Question 6

Context Window 為什麼是 4096？上下文視窗的物理本質

🧭 第一性原理：三道閘門

Context window 是 prompt + generated 的硬性上限。它由三件互相獨立的事共同決定，任何一個壞了就崩潰：

  1. 位置編碼上限（結構性硬限制） — RoPE 預先算好的 freqs_cos/sin 緩衝區形狀就是 [max_position_embeddings, head_dim]。超過就 IndexError。
  2. 訓練資料分佈 — 模型在訓練時只看過 N 以內的序列，超過就「沒學過」，語意完全崩壞。
  3. 計算與記憶體成本 — 注意力 O(L²)，KV cache 線性增長。從 4K → 32K：注意力成本變 64 倍。

🤔 為什麼是 4096 這個具體數字？

三個原因匯流而成：

  • 2 的次方 — GPU 記憶體 tiling、kernel block 大小、CUDA warp（32）都偏好 2 的次方。4096 = 2^12 整齊。
  • 2023 經濟甜蜜點 — LLaMA-1 用 2048，LLaMA-2 翻倍到 4096。翻倍 context = 4 倍注意力成本。4K 是 Meta 當時負擔得起的最大值，業界跟著抄。
  • 多數文件長度 — 大部分網頁、程式碼檔、書本章節都在 4K 以內，超過要做資料工程。

🚀 MiniMind2 如何走得更遠：YaRN

MiniMind2 預設 32K，啟用 --inference_rope_scaling 後可以推到 128K — 而且不需要重新訓練！

model_minimind.py:108-128 — YaRN: Yet another RoPE extensioNdef precompute_freqs_cis(dim, end=int(32 * 1024), rope_base=1e6, rope_scaling=None):
    freqs = 1.0 / (rope_base ** (torch.arange(0, dim, 2)[: (dim // 2)].float() / dim))
    if rope_scaling is not None:
        orig_max, factor, beta_fast, beta_slow = ...
        if end / orig_max > 1.0:
            # ★ YaRN 只「擠壓」會走樣的低頻維度，高頻維度保持原樣
            corr_dim = next((i for i in range(dim // 2)
                            if 2 * math.pi / freqs[i] > orig_max), dim // 2)
            power = torch.arange(0, dim // 2, ...).float() / max(dim // 2 - 1, 1)
            beta = beta_slow + (beta_fast - beta_slow) * power
            # λ = (β·α - β + 1)/(β·α) YaRN標準公式
            scale = torch.where(torch.arange(dim // 2, ...) < corr_dim,
                                (beta * factor - beta + 1) / (beta * factor),
                                1.0 / factor)
            freqs = freqs * scale
💡 YaRN 的精妙之處
傳統 Position Interpolation 對所有頻率一視同仁地壓縮，破壞了高頻表徵。YaRN 用 corr_dim 區分「該壓的低頻」和「該保留的高頻」— 是分段處理，所以原本訓練學到的表徵被最大程度保留。

Question 8

串流輸出 TextStreamer & TTFT vs TPOT

🧭 第一性原理

沒有串流：使用者等待 TTFT + (output_len × TPOT) 後一次看到全部答案。
有串流：使用者在 TTFT 後馬上看到第一個字，然後每 TPOT 間隔出現下一個字。

📍 程式碼定位

eval_llm.py:63 — 本地 CLI 串流streamer = TextStreamer(tokenizer, skip_prompt=True, skip_special_tokens=True)

scripts/serve_openai_api.py:59-68 — Server-Sent Events 串流class CustomStreamer(TextStreamer):
    def __init__(self, tokenizer, queue):
        super().__init__(tokenizer, skip_prompt=True, skip_special_tokens=True)
        self.queue = queue

    def on_finalized_text(self, text: str, stream_end: bool = False):
        self.queue.put(text)        # 每生成一個 token 就推入佇列
        if stream_end:
            self.queue.put(None)    # 結束標記
🎯 操作面的關鍵啟示
  • Prefill 成本 = TTFT：影響使用者感受到的「停頓」
  • Decode 成本 × 輸出長度 = 串流總時長：每個 token 很快但累積
  • KV cache 只幫 TPOT，幫不到 TTFT — 若要改善重複請求的 TTFT，需要跨請求的 prefix caching
